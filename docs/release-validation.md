# Release validation gate

`test/full-regression-gate` is the integrated production-readiness regression gate. It does not replace feature-specific tests and must not be made green by lowering assertions. Fix test-environment defects in the gate; when a real application bug is found, add the regression that proves the fix.

## Safety invariants

Release validation must never depend on production/customer state or credentials.

- PostgreSQL and Valkey must be disposable local/CI services. `scripts/qa/assert-test-env.ts` rejects remote `DATABASE_URL` and `REDIS_URL` values.
- `LOAD_ALLOW_REMOTE=1` is forbidden by the regression gate.
- Campaign load traffic uses the existing local fake Meta redirect and fake Graph API. Do not provide a real Meta access token.
- R2 values used by security tests are synthetic signing placeholders only. The gate does not require a real R2 account or object bucket.
- Browser users, workspaces and records are generated by the tests; verification email is captured to a local JSONL file.
- Chaos runs use `docker-compose.load-chaos.yml`, local ports and disposable volumes. They must never target customer PostgreSQL or Valkey.

## Canonical release flow

From a clean checkout, with disposable PostgreSQL and Valkey available, run:

```bash
export DATABASE_URL=postgres://whatsapp:whatsapp@127.0.0.1:5432/whatsapp
export REDIS_URL=redis://127.0.0.1:6379
export BETTER_AUTH_URL=http://127.0.0.1:3000
export BETTER_AUTH_SECRET=test-only-better-auth-secret-that-is-long-enough
export AUTH_EMAIL_CAPTURE_FILE=/tmp/wa-auth-emails.jsonl
export META_GRAPH_API_VERSION=v26.0
export META_APP_ID=123456789
export META_APP_SECRET=test-only-meta-secret
export META_CONFIG_ID=test-only-config-id
export META_VERIFY_TOKEN=test-only-verify-token
export CREDENTIAL_ENCRYPTION_KEY="$(openssl rand -base64 32 | tr -d '\n')"

bun run qa:release
```

The portable flow validates, in order: environment safety, frozen dependency installation, coverage-manifest drift, migration drift, clean migrations and schema verification, unit/integration tests, critical webhook reliability regressions, typecheck, production web build, full browser E2E, security E2E, dependency audit, 1k campaign/webhook load smoke and a 1k worker-restart resilience smoke. Gitleaks and CodeQL remain GitHub Actions checks because they depend on repository-history/security-event context.

For release candidates, prefer the `Full Regression Gate` GitHub Actions workflow. Its core, full-browser, security and load/resilience jobs each create or own clean infrastructure so one suite cannot silently depend on state left by another. The final `Release gate` job only succeeds when every lane succeeds.

## Pull-request checks versus heavy validation

Routine pull requests should remain fast enough to be required. `CI` runs migration drift/schema verification, unit/integration tests, typecheck, production build, coverage drift and a desktop browser smoke. `Security` separately runs dependency audit, Gitleaks, CodeQL and the clean security E2E suite. Production container validation remains path-triggered in `Production Infra`.

Do not run 500k datasets, long soak tests or destructive chaos on ordinary GitHub-hosted PR runners. `.github/workflows/heavy-validation.yml` is manual and requires a runner labelled `self-hosted`, `linux`, `x64`, `qa-load`. It owns the 500k campaign benchmark, 100k webhook flood, 500k reporting dataset, soak and destructive chaos selections.

Before a production launch, a staging/VPS runner representative of the intended deployment should run the existing load harness progressively rather than jumping directly to 500k:

```text
1k -> 10k -> 50k -> 100k -> 500k recipients
```

Run the 80 MPS and 1,000 MPS campaign paths, concurrent/multi-organization cases, slow Meta, 429/5xx storms and webhook floods. The 500k / 80 MPS run is intentionally long and belongs on staging/VPS, not routine CI. Repeat Redis restart, worker restart, PostgreSQL pressure and multi-worker scenarios there as well.

## Coverage manifest

`qa/coverage-manifest.ts` is the QA inventory for pages, API routes, major workflows, roles, security boundaries and load scenarios. `bun run qa:coverage` walks every current Next.js `page.tsx` and `route.ts` source and fails when a new source is not registered. It also fails stale file references and malformed coverage entries.

An existing uncovered surface may be registered as `gap` only with an explicit reason. A `gap` does not count as covered. Feature changes should normally land with an executable test reference and move the entry to `partial` or `covered`. This makes route growth visible without pretending current gaps do not exist.

The snapshot used to create this gate records 51 logical pages and 20 API routes. Current browser/security coverage is strong for public pages, onboarding, responsive/i18n rendering, tenant isolation and request-boundary abuse, but known gaps remain around account recovery/MFA, team and WhatsApp connection workflows, platform-admin browser behavior and several complete happy-path lifecycles. See the manifest for the exact status and regression references.

## GitHub branch protection recommendation

At the time this gate was created, `main` was not marked protected by the GitHub branch endpoint. Recommended required checks for `main` after this branch is reviewed are:

- `CI / CI`
- `CI / Browser smoke`
- `Security / Security gate`
- `Production Infra / validate` when its path filter applies; do not make a path-skipped job a universal required check unless repository rules handle that case correctly.

Also require pull requests, prevent force pushes/deletions, dismiss stale approvals after new commits and require conversation resolution. Keep `Full Regression Gate / Release gate` as a release/staging promotion check rather than adding its heavier lanes to every PR.

Repository policy changes are deliberately not made by this branch; the gate documents the recommended settings for an administrator to apply after review.
